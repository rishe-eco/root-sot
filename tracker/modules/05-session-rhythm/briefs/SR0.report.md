## 4. Decisions the card didn't make

1. **`gatherKey` dedup query reads every gathered row for the user's own templates, not just the current window.** D-2's bug is exactly that a moved/retimed row's *current* `forDate` falls outside the window being gathered, so limiting the read to `forDate: { in: forDates }` would still miss it. I widened the read to `sourceId: { in: <this user's interval/routine ids> }` with no `forDate` filter — correct for any size of history, but it is an unbounded-by-date read; a user with years of a daily interval would read every row that interval ever produced. Nothing in the plan bounds this, and D-17's growth table doesn't name a cap on gathered-action count. Flagging for the reviewer rather than adding a cap unasked.
2. **`orderDay`'s return type is `Boolean!`, not a list of actions.** No screen in SR0 reads an ordered result, and the card doesn't say. `Boolean!` matches the house pattern for a write nothing reads back yet (`deleteFocusPeriod`, etc.); SR2 can add a richer return if a screen ends up wanting one.
3. **`ensureRhythm`'s return type is `RhythmStatus`, the same shape as `rhythmStatus`**, rather than a separate `RhythmState` type. One round trip for a caller that needs both, and the card's decision 1 only commits to `rhythmStatus`'s shape being testable — reusing it for `ensureRhythm` doesn't violate that and avoids a second near-duplicate type.
4. **`services/rhythm/rhythmState.ts` is a third file**, beyond the card's named `days.ts`/`dayList.ts`. `ensureRhythm`/`rhythmStatus` don't fit either file's subject (day-planning rules vs. one day's list), and the card's Logic section describes them as their own bullet.
5. **Action/Interval/Routine's new columns are not added to the GraphQL `Action`/`Interval`/`Routine` SDL types.** Nothing in SR0's screens or logic reads them through GraphQL — `dayList`/`orderDay` read/write them server-side only. SR1 (crossing, `reviewSetting`) and SR3 (capture, review-setting forms) are where client exposure actually gets used; adding it now would be unused surface.
6. **The four new enums (`ReviewSetting`, `RhythmAnswer`, `RhythmFollowUp`, `GapChoice`) are declared in `schema.prisma` only, not in the GraphQL SDL**, for the same reason as #5 — nothing in SR0 exposes a field typed by them yet.
7. **`orderDay`'s "same group" check compares `plannedDayKey(action) === dateKey`, not just that the ids agree with each other.** The card's refusal table names the message but not exactly what triggers it; reading it literally ("ids across start times or days") meant an id merely planned on a *different* day than the `dateKey` argument also has to refuse, not just a cross-time-within-the-right-day mix.
8. **`addAction`/`addProject`'s per-action `firstDueKey` set directly from the new date, not through `freezeFirstDue`.** A brand-new row has no prior `firstDueKey` and no prior date, so `freezeFirstDue`'s "already frozen, else freeze the current date" logic degenerates to "use the new date" anyway, but writing it as a direct `plannedDayKey(...)` call at the two create sites reads clearer than calling a freeze function on a row that doesn't exist yet.

## 5. Where the plan, card or brief was wrong, vague or incomplete

1. **The migration mechanism is SQLite's "RedefineTables" table rebuild, not a plain `ALTER TABLE ADD COLUMN`.** Prisma's generated SQL for `Action`/`Interval`/`Routine` drops and recreates each table with an `INSERT INTO new_X SELECT ... FROM X` copy, because the new non-nullable `reviewSetting` column (with a default) triggers SQLite's rebuild path. The card's trap ("no `UPDATE` of an existing row") reads as ruling out a literal `UPDATE` statement, which this migration has none of — but it's worth saying explicitly that the rebuild-and-copy *is* what AC-6 accepts, since on a first read it looks more invasive than "add a column."
2. **The card doesn't say what `orderDay` refuses when ids span different *days*** (only "within one start time" is named in §6.2's message and the card's own description). I read the single refusal message as covering both cases (cross-time and cross-day), since the plan's §2.2 #8 only ever describes ordering "within a day." Worth the reviewer confirming the one-message reading is intended rather than wanting a second, more specific refusal.
3. **PD-3's "the formula on the row's fields" fallback and the widened existing-rows read interact in a way the card doesn't spell out.** The card says the dedup key is `gatherKey ?? gatheredActionKey(row)`, which is a one-line change; getting D-2 (move/retime) to actually not recreate a row required also widening *which* rows get read into the `seen` set before that key is computed (item 4.1 above) — the card's text reads as if changing the key formula alone would fix it, but the old query's `forDate: { in: forDates }` filter would still have excluded a moved row.
4. **The card's decision 4 (schema assertions) says "if [`schema.unit.test.ts`] reads the file" — it reads `typeDefs.ts`, the GraphQL SDL, never `schema.prisma`.** So the new `rhythmSchema.unit.test.ts` was the right call per the decision's own fallback, but the phrasing briefly reads as if the answer were still open; confirmed by reading `schema.unit.test.ts` itself before writing the new file.

## 6. What I couldn't verify

- **The actual production migration path (an existing deployed database running the migration at boot).** Only run against a fresh worktree test/dev database. The card says this isn't SR0's concern (no deploy happens here), but it's the one thing that would fully confirm AC-6 on real data rather than on fixtures created in this session.
- **`orderDay`'s write to a gathered row's interval/routine source** is verified to persist the right value, but not that a *later gather* actually reads that `sortOrder` back onto a brand-new occurrence — `dayList`'s own sort does read `Action.sortOrder`, but nothing in SR0 copies a template's `sortOrder` onto an occurrence at gather time *from an edit made after the occurrence already exists* (gathering only copies at create). That's consistent with spec §2.2 #8 ("the next occurrences keep it" — future ones, not the one already gathered), but there's no SR0 test that walks a full "order today's gathered row → re-gather → next occurrence has the order" cycle, since that requires a second gather on a later date.
