## What to build

Plan §5 B3, into B2's components. B2 left these hooks for you; use them rather than restructuring:

- **`FocusProjectCard` props:**
  - `onComplete(action)` enables the checkbox.
  - `onDayClick(action)` turns the day chip into a button.
  - `renderBelowRow(action)` is the reschedule popover's slot, under the row.
  - `onAddAction()` shows "+ Action".
  - `addForm` replaces "+ Action" while the inline form is open.
  - `menu` is the ⋯ menu node, top right.
- **`FocusPage.tsx`:** `deriveState()` returns `"lookback"` first when `overview.lookback` is set. Render `FocusLookback` then. After Done, refetch: the page then falls through to active, upcoming or empty (AC-10).
- **`FocusPeriodForm`** takes `initial={{ startDate, projectIds }}` in create mode, and already shows "carried over" against those ids. The look-back's "Start a new period with these" opens it that way (AC-24). The start is `max(lookback.endDate + 1 day, today)` (AC-25); use `addDaysToDateKey` from `~/utils/dateUtils`.

The code check turned up two things the plan didn't know:

- **The server does not enforce the estimate on reschedule.** `updateAction` validates `estimatedTimeMinutes` only when it's sent (`mutations.ts:152-155`), so `tbd` without minutes on an action with no estimate *succeeds*. AC-18 therefore has to be enforced in the popover:
  - if the action's `estimatedTimeMinutes` is null and a day is picked, Save stays disabled until minutes are given (0–1440);
  - send `tbd` and `estimatedTimeMinutes` together.
  - "Clear day" sends `tbd: null` (the resolver clears it, `mutations.ts:160`).
  - The test must assert that a `tbd` is never sent without minutes for such an action.
- **`ADD_PROJECT_ACTION`** already takes `projectId`, `tbd` and `estimatedTimeMinutes`. Use it as is. `addAction` *does* refuse `tbd` without minutes (`mutations.ts:127-128`), but enforce it in the form anyway (W5: Minutes appears once a day is picked).
