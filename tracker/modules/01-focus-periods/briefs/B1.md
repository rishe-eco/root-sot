## What to build

Exactly plan §5 B1:
- the two models and their back-relations, and migration `add_focus_periods`;

- the GraphQL types, 2 queries and 4 mutations;

Points the plan leaves to you, or that the code check turned up:

- **Date keys.** Validate with a `YYYY-MM-DD` regex *and* a round-trip (`new Date(key + "T00:00:00.000Z").toISOString().slice(0,10) === key`), so `2026-02-30` is refused. Store with `dateKeyToDate`'s pattern. Return `startDate`/`endDate` as `YYYY-MM-DD` from `typeResolvers.ts`, the way `Action.forDate` is (`typeResolvers.ts:31`). The private `validateDateKey` at `mutations.ts:921` checks the regex only and throws a different message, so write your own in the service and leave that one alone.
- **`FocusPeriod.projects` resolver.** Return the `Project` rows ordered by the join's `addedAt` ascending. Include `actions`, `goal`, and `milestone: { include: { goal: true } }`, so the existing `Project` type resolvers short-circuit on loaded data.
- **`updateFocusPeriod` input.** Every field in `FocusPeriodInput` is required: the Edit sheet always sends all of them (PD-5). `title` is trimmed, 1–120 characters.
- **Where the rules live.** Rules go in the service. The resolvers are thin (Convention 5's spirit), and each one calls `ensureOwned` on the period before the service touches it.
- **`isProjectDone`.** It mirrors `getProjectStatus`'s "Done" branch (`client/app/components/projects/ProjectPreview.tsx:57-64`): `actions.length > 0 && actions.every(a => a.done)`. Put a comment on it naming that file and function. Don't edit the client.
